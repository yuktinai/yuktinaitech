Android SDK

AMOS SDK for modern monetization-aware Android apps.

Integrate AMOS into Android apps with either a wrapper-serving AdMob module or a manual-serving core module. The SDK connects runtime tracking, user segmentation, and monetization decisions without exposing backend complexity to the host app.

Why teams use it

Clean monetization tooling without extra app complexity.

  • Choose between a fast AdMob wrapper integration or a more controlled manual-serving path.
  • Track events and metrics safely through SDK helpers.
  • Read monetization segment state for ad, subscription, and hybrid experiences.
  • Keep decisions centralized in the backend and admin UI while the SDK handles runtime coordination.

Step 1

Choose the artifact

Use `mavenCentral()` in your Android project repositories, then choose the integration style that fits the publisher contract.

dependencyResolutionManagement {
    repositories {
        google()
        mavenCentral()
    }
}

dependencies {
    // Wrapper-serving AdMob integration
    implementation("com.yuktinai:amos-sdk-admob:1.0.1")

    // Or manual / hybrid serving
    // implementation("com.yuktinai:amos-sdk:1.0.1")
}

Step 2

Initialize the SDK

Provide your app API key, app identifier, and user identifier at session start.

Monetization.init(context, "API_KEY", "APP_ID", "USER_ID") {
    val state = Monetization.getState()
    val segment = state.userSegment
    val allowedEvents = state.allowedEvents
    val allowedMetrics = state.allowedMetrics
}

Step 3

Wrapper-serving setup

If you use the wrapper artifact, add the AdMob app ID placeholder and register local ad groups.

android {
    defaultConfig {
        manifestPlaceholders["amosAdMobAppId"] = "ca-app-pub-xxxxxxxxxxxxxxxx~yyyyyyyyyy"
    }
}

AmosAdMob.configure(
    AdMobConfig(
        interstitialGroups = mapOf(
            AdMobConfig.DEFAULT_GROUP_REF to AdMobGroupConfig(
                unitIds = listOf("ca-app-pub-xxx/111"),
                preloadOnInit = true
            )
        )
    )
)

Integration flow

What the app team does

  1. Initialize `Monetization` with `API_KEY`, `APP_ID`, and `USER_ID`.
  2. Read SDK state after init and consume the resolved user segment when needed.
  3. Track allowed events and metrics through the SDK during the session.
  4. If using the wrapper artifact, initialize `AmosAdMob` and call wrapper methods for interstitial, rewarded, and banner flows.
  5. If using the core artifact, integrate Google Mobile Ads directly and use the AMOS planning APIs for request, preload, and lifecycle callbacks.
  6. End the AMOS session when appropriate with `Monetization.endSession()`.

Wrapper path

Use the AdMob wrapper

The wrapper module includes Google Mobile Ads and owns the provider bridge while keeping AMOS runtime decisions centralized.

Monetization.init(context, "API_KEY", "APP_ID", "USER_ID") {
    AmosAdMob.initialize(context)
}

AmosAdMob.showInterstitial(activity)

AmosAdMob.showRewarded(
    activity = activity,
    onRewardEarned = { /* reward user */ }
)

Core path

Use manual or hybrid serving

The core artifact is for publishers who want tighter control over the provider SDK and ad orchestration.

val request = Monetization.getAdMobInterstitialRequest("default")

val preload = Monetization.preloadAdMobInterstitial("default")

Monetization.markAdMobInterstitialLoaded(groupRef, loadedAd)
Monetization.recordAdMobInterstitialShown(groupRef)

Runtime model

What AMOS handles behind the scenes

  1. Session start and end.
  2. Backend-driven segment and monetization decision resolution.
  3. Allowed event and metric filtering.
  4. AdMob request planning, preload planning, rotation, and fallback logic.
  5. Coordination with backend Value Engine and decision policies configured in the admin UI.

Naming

How to read the package names

  1. Publishers install 1 of 2 Maven artifacts: `com.yuktinai:amos-sdk-admob` or `com.yuktinai:amos-sdk`.
  2. The repo uses matching Gradle module names: `:amos-sdk-admob` and `:amos-sdk`.
  3. Android app code imports Kotlin packages such as `com.yuktinai.amos.sdk` and `com.yuktinai.amos.sdk.admob`.
  4. The artifact and Gradle names now align, while Kotlin namespaces stay stable for app code.

Policy model

What the backend decision can control

  1. Interstitial: enabled, preload, cooldown, max per session, override unit IDs.
  2. Banner: enabled, refresh seconds, override unit IDs.
  3. Rewarded: enabled, preload, promoted, reward type and amount, override unit IDs.
  4. Paywall: enabled, variant, trigger.
  5. CRM canvas and UA value multiplier.

What to prepare

Before the app team starts

  • A valid AMOS `API_KEY` and `APP_ID`.
  • An agreed user identifier strategy for the host app.
  • Android Internet permission in the app manifest.
  • An integration choice: `amos-sdk-admob` wrapper-serving or `amos-sdk` manual-serving.
  • If using the wrapper: AdMob app ID and local ad-unit group configuration.
  • A clear place in the app where segment state will be consumed.
